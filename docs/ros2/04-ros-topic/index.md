## 一、直觉与工具

### 1.1 机器人是一个团队，不是一个程序

打破固有印象：机器人不是"一个巨大的单一程序"，而是**由无数独立的小人（Node，节点）组成的团队**——视觉节点负责看，决策节点负责想，运动节点负责跑。这正是工程师眼中的**微服务架构**，而 ROS 就是让它们协作的粘合剂。

![机器人不是一个人，而是一个团队](./images/p004-01.webp)

### 1.2 发布/订阅模型（Pub/Sub）

节点之间怎么交流？不是"打电话"（点对点、效率低），而是像机场塔台广播：**发布者只管发，订阅者只管收，彼此不认识**。

- **发布者（Publisher）**：塔台，把消息喊到"广播频道"。
- **话题（Topic）**：广播频道，是连接节点的通道。
- **消息（Message）**：广播的内容，例如"天气晴朗"。
- **订阅者（Subscriber）**：飞行员，调好频道就能收到，不用关心谁在播。

![发布/订阅模型](./images/p005-02.webp)

> [!TIP] 一句话记住
> Topic 是连接节点的"广播频道"，高效又灵活。

### 1.3 工业界为什么非要用 Pub/Sub

两个核心词：

- **异步（Asynchronous）**：发送者发完就走，无需等待回复。
- **解耦（Decoupling）**：双方只需约定 Topic 名字，互不认识也能协作。雷达团队只管发雷达数据，底盘团队只管收；就算把雷达换成摄像头，底盘代码一行都不用改。

![异步与解耦](./images/p006-03.webp)

这正是 ROS 能支撑起数百万行代码的复杂机器人项目的秘密。

### 1.4 三个核心"行话"

| 概念                | 比喻           | 说明                                   |
| ------------------- | -------------- | -------------------------------------- |
| **Node（节点）**    | 干活的工人     | 执行具体任务的最小单元                 |
| **Topic（话题）**   | 输送带         | 节点之间传递数据的通道                 |
| **Message（消息）** | 输送带上的包裹 | 一次传递的实际数据，如速度、位置、指令 |

![Node / Topic / Message](./images/p007-04.webp)

> 这三个概念将贯穿我们整个职业生涯。

### 1.5 动手：认识实验主角 Turtlesim

启动小海龟模拟器：

```bash
ros2 run turtlesim turtlesim_node
```

它本身就是一个完整的 ROS2 节点：一边**广播**自己的位置信息（Pub），一边**监听**速度指令（Sub）。

![启动 Turtlesim](./images/p008-05.webp)

### 1.6 系统诊断三件套

像医生看病一样检查 ROS2 系统：

**第一步：查户口 —— 看有哪些话题**

```bash
ros2 topic list
```

输出里能看到 `/turtle1/pose`、`/turtle1/cmd_vel` 等频道。

**第二步：用听诊器 —— 实时查看数据流**

```bash
ros2 topic echo /turtle1/pose
```

海龟会实时汇报坐标与朝向，相当于拥有了"上帝视角"。

![诊断：topic list 与 topic echo](./images/p009-06.webp)

**第三步：手动接管 —— 用命令行强行发指令**

```bash
ros2 topic pub /turtle1/cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 2.0, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 1.8}}"
```

回车后海龟开始转圈。在工程调试中，这是**验证电机好坏最快的方法**。

![手动发布指令](./images/p010-07.webp)

## 二、标准开发实战

### 2.1 工作空间与功能包

把 ROS2 代码想成做菜：

- **工作空间（Workspace）**＝"厨房"，存放所有项目的地方。
- **功能包（Package）**＝"备菜区"，具体的代码、配置、资源放在这里。

ROS2 对目录结构非常严格，包必须放在 `src/` 下：

```text
~/ros2_ws/src/my_package/   正确，ROS 能找到
~/ros2_ws/my_package/       错误，ROS 找不到
```

![工作空间与功能包](./images/p013-09.webp)

### 2.2 第一个节点：`__init__` 里的秘密

一个节点在 `__init__` 里做两件事：**注册自己** + **声明要发布的话题**。

```python
from rclpy.node import Node
from geometry_msgs.msg import Twist

class MyFirstNode(Node):
    def __init__(self):
        # 1. 告诉 ROS “我上线了”
        super().__init__('my_first_node')
        # 2. 建立发布者（广播专栏）
        self.pub = self.create_publisher(
            Twist,
            '/turtle1/cmd_vel',
            10                 # 队列长度
        )
```

就像在广播站注册了一个专栏，准备好大声广播。

![__init__ 的类比](./images/p014-10.webp)

### 2.3 编程灵魂：定时器回调（Timer Callback）

不要用 `while` 循环"忙等待"检查时间——那会一直占用 CPU。ROS 的做法是**事件驱动**：定时器 0.5 秒"叫醒"你一次，你处理完就继续睡。

```python
# 唤醒 -> 打包消息 -> 发送 -> 继续睡
self.timer = self.create_timer(0.5, self.callback)
```

| 传统思维             | ROS 之道                   |
| -------------------- | -------------------------- |
| `while` 循环，忙等待 | 事件驱动，Sleep & Wait     |
| 效率低，占用 CPU     | 不占用 CPU，需要时才被叫醒 |

![定时器回调](./images/p015-11.webp)

### 2.4 开发五步法

十年经验总结的开发流程，**Config 和 Source 千万别忘**：

| 步骤 | 名称                   | 说明               | 对应命令                    |
| ---- | ---------------------- | ------------------ | --------------------------- |
| 1    | Create（创建包）       | 打地基，建新家     | `ros2 pkg create ...`       |
| 2    | Code（写代码）         | 写脚本，赋灵魂     | Python / C++                |
| 3    | **Config（配置）**     | 办户口，登记入口点 | 编辑 `setup.py`             |
| 4    | Build（编译）          | 照图纸，造实体     | `colcon build`              |
| 5    | **Source（刷新环境）** | 通电源，激活它     | `source install/setup.bash` |

> [!CAUTION] 90% 的调试时间都坑在这里
> 改了代码却忘了 `source`，节点还是旧行为。务必把这一步刻在脑子里。

![ROS2 开发五步法](./images/p016-12.webp)

配置入口点在 `setup.py`：

```python
entry_points={
    'console_scripts': [
        'my_node = my_package.my_node:main',
    ],
},
```

### 2.5 小海龟速度控制：线速度与角速度

坐标接口约定：**原点在左下角 (0,0)，X 轴向右，Y 轴向上**。

## 三、架构进阶：六轴机械臂

### 3.1 项目主角：控制与反馈

六轴机械臂是典型的"执行 + 反馈"系统：

- **驱动部分（执行器）**：控制 6 个关节，运动到指定角度。
- **传感部分（编码器）**：实时读取关节角度，提供位置反馈。
- **通信**：与上位机通过串口（UART/USB）通信。

![六轴机械臂：控制与反馈](./images/p020-19.webp)
![机械臂实物](./images/p020-18.webp)

### 3.2 需求一：遥操作，实时发布关节角

**背景**：手动摇动机械臂时，实时把关节角度发布出去。

**流程**：创建节点 → 读取关节角 → 自定义消息 → 发布消息 → 测试。

使用手柄遥操作，节点读取 6 个关节角（J1–J6），以 `/joint_states` 话题发布出去。

![遥操作与发布](./images/p021-20.webp)
![驱动节点五步流程](./images/p022-21.webp)

### 3.3 需求二：订阅角度，驱动关节

**背景**：订阅其他节点发送的角度，让机械臂运动到指定角度。

控制节点把目标角度发布到 `/cmd_angles`（类型 `float32[]`），机械臂控制节点 `/arm_controller` 订阅后驱动 J1–J6 运动。

![角度控制订阅](./images/p023-22.webp)
![开发与测试流程](./images/p024-23.webp)

> [!NOTE] 节点分工
> **驱动节点**负责关节控制与反馈；**逻辑节点**负责上层业务（如录制、回放）。两者通过 `/joint_states` 与 `/cmd_angles` 两个话题连接。

### 3.4 需求三：动作录制与回放

![驱动节点与逻辑节点分层](./images/p025-24.webp)

**录制流程**：创建节点 → 订阅关节角 → 存储时间+角度信息 → 提供启停接口。

- 订阅 `/joint_states`（关节角）
- 把**时间戳 + 角度**存入文件/数据库
- 通过 `ros2 service call /start_record` 或按钮控制启停

![录制节点](./images/p026-25.webp)

**回放流程**：创建节点 → 读取解析文件 → 按时间播放 → 启停操作。

- 读取文件，按时间顺序解析
- 按时间轴发布到 `/cmd_angles`
- 通过 `ros2 service call /start_playback` 控制

![回放节点](./images/p027-26.webp)

### 3.5 功能整合与分层架构

把录制和回放合并到一个节点 `arm_record_playback_node`，对外只暴露一个服务 `/control_record_playback`，避免功能冲突。

![功能整合](./images/p028-27.webp)

再叠加 UI，形成分层架构：

| 层     | 节点                       | 职责                                  |
| ------ | -------------------------- | ------------------------------------- |
| UI 层  | `gui_record_playback_node` | 用户交互，通过 `/ui_control` 服务控制 |
| 逻辑层 | `arm_record_playback_node` | 录制回放业务逻辑 + 数据存储           |
| 驱动层 | `arm_joint_node`           | 控制电机、读取传感器（实时控制）      |

![分层架构](./images/p029-28.webp)

### 3.6 launch 一键启动

手动开三个终端分别 `ros2 run` 太麻烦，用 launch 文件一次启动所有节点：

```xml
<launch>
  <node name="arm_joint_node" .../>
  <node name="arm_record_playback_node" .../>
  <node name="gui_record_playback_node" .../>
</launch>
```

```bash
ros2 launch pkg system.launch
```

![ROS launch 一键启动](./images/p030-29.webp)

## 四、综合实战应用：自动驾驶 AEB

### 4.1 给海龟装上"翻译"

问题：海龟只吐原始坐标 `(x: 5.5, y: 5.5)`，而 AEB 工程师只想知道"前面还有几米、会不会撞"。

解决方案：在两者之间加一层**翻译节点（Translator Node）**，把坐标换算成**距离**和**风险**。

![AEB 翻译层](./images/p031-30.webp)

### 4.2 自定义 Msg：接口契约

感知组和控制组约定一个消息格式 `RadarScan.msg`，这就是**接口契约**——只要消息符合契约，双方就能协作，无需关心对方代码实现。

```text
# RadarScan.msg
float32 distance      # 距离
bool    risk_warning  # 是否危险
```

![自定义 Msg 接口契约](./images/p032-31.webp)

### 4.3 编译与验收

自定义消息底层依赖 C++ 工具链，所以要在 `CMakeLists.txt` 里注册（标准流程，照抄即可）。

![编译魔法](./images/p033-32.webp)

编译完成后验证：

```bash
ros2 interface show <your_msg_name>
```

能看到 `float32 distance` 和 `bool risk_warning` 就说明成功——你刚刚创造了属于这台机器人的"方言"。

![验收：创造方言](./images/p034-33.webp)

### 4.4 三层架构：感知 → 决策 → 控制

| 层       | 角色     | 说明                                  |
| -------- | -------- | ------------------------------------- |
| **感知** | 数据源头 | 模拟器 → 雷达节点，清洗与翻译原始信息 |
| **决策** | 智能中枢 | AEB 节点，分析风险、制定策略          |
| **控制** | 执行动作 | 输出控制指令，紧急制动                |

这正是特斯拉、Waymo 等自动驾驶公司架构的雏形。

![系统架构总览](./images/p036-34.webp)

### 4.5 感知层：数据抽象与语义提取

**数据抽象**：墙在 11 米处，海龟当前位置 x，则距离 = 11 − x。

```python
distance = 11.0 - msg.x
```

**语义提取**：距离小于 2 米时，把冰冷的数字变成判断。

```python
risk_warning = True   # 有危险！
```

> [!IMPORTANT] 单一职责原则
> 感知层只负责喊"有危险"，**不负责踩刹车**。一定要管住自己的手。

![数据抽象](./images/p037-35.webp)
![语义提取](./images/p038-36.webp)

写完感知层，**先测试再前进**：运行节点、监听 `/radar_scan`，检查距离是否变小、`True` 是否在 2 米以内出现。

![感知层验证](./images/p039-37.webp)

### 4.6 决策层：盲目信任与解耦精髓

决策层是一个"盲人"——它看不见海龟在哪，只**完全信任**雷达发来的消息。这种"盲目信任"正是解耦的精髓：**只关注消息本身，无需知晓对方是谁或如何工作**。

![决策层：盲目信任](./images/p040-38.webp)

### 4.7 控制层：系统的大脑

没有任何复杂的计算，只有最纯粹的逻辑判断：

```python
if warning is True:
    speed = 0     # 刹车
else:
    speed = 1     # 巡航
```

![控制逻辑](./images/p041-39.webp)

### 4.8 最终联调 Demo

1. 依次启动：模拟器、雷达节点、AEB 节点
2. 海龟接近墙壁：3 米 → 2 米……
3. 在 2 米处成功制动，毫厘不差

![最终联调](./images/p042-40.webp)

### 4.9 总结与展望

从一只"只会乱跑的海龟"，到具备自动避障功能的智能机器人，靠的是四块拼图：

1. 海龟（原始能力）
2. **ROS2 Topic 机制**（Pub/Sub）
3. **自定义消息**（接口设计）
4. **分层架构**（感知 → 决策 → 控制）

![总结与展望](./images/p043-41.webp)

## 本章小结

- **模型**：Pub/Sub 三个概念——Node 干活、Topic 传话、Message 是内容。
- **诊断**：`ros2 topic list / echo / pub` 三件套，配上 `rqt_graph` 看图。
- **五步法**：Create → Code → **Config** → Build → **Source**，后两步最容易忘。
- **架构**：驱动节点管实时控制，逻辑节点管业务；录制/回放靠服务启停。
- **实战**：AEB 分三层——感知出语义、决策只信任消息、控制只做判断。
